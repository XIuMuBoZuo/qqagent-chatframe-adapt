# 通用踩坑规则登记表



每条规则按 **症状 → 原因 → 修法 → 验证 → 适用范围/来源** 五段登记。

「适用范围」明确写清这条结论是从哪个项目、哪套环境得出的，**不要把单一项目的结论推广到所有环境**。



规则编号规则：`R-类别-序号`。新增规则追加在对应类别末尾，不改动既有编号。

## 类别 A：路径与迁移



### R-A-01 搬家后脚本仍写回旧桌面路径



- **症状**：工程整体搬到新目录后，重跑交付脚本，产物又出现在旧的 `C:\Users\...\Desktop\...` 位置，和整理好的目录结构对不上。

- **原因**：脚本里 `DEST` / 输出路径是硬编码的绝对路径，搬家不改变脚本内容。

- **修法**：路径一律从脚本自身位置推导，例如 `os.path.join(os.path.dirname(ROOT), "子目录名")`；工程怎么搬，产物就落在它旁边。禁止在脚本里写死 `C:\Users\...` 或任何用户盘符。

- **验证**：把工程复制到一个不同盘符的临时目录，跑一次 `--dry-run`，确认打印出的目标路径全部落在新工程同级目录下，且不再出现旧绝对路径。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-29（原文《建模总结_踩过的坑》12.7）。**通用**：适用于任何会被搬动的工程。注意这是**修法方向**，不是「所有脚本都已经改好了」的断言。



### R-A-02 盘点目录时跟随 Junction，导致同一份数据被数两遍



- **症状**：迁移清单里同一个目录出现两次（一次按桌面路径、一次按真实路径），估算体积翻倍；或递归遍历时进入回环，扫描不结束。

- **原因**：Windows Junction / 符号链接在普通枚举下看起来就是普通目录，`Get-ChildItem -Recurse` 会跟进去；桌面 `AI产物归档`、`kanata_*` 都是 Junction。

- **修法**：**先解析链接真实目标再决定是否遍历**：

  ```powershell

  Get-Item -Force $p | Select-Object Name, @{n='T';e={$_.Target -join ';'}}, Attributes

  # Attributes 含 ReparsePoint 即链接

  ```

  在清单里**同时记录来源路径和真实路径**，并把二者标记为同一实体的两种视图；遍历时对 ReparsePoint 不再深入。

- **验证**：`source_inventory.json` 中不存在两条记录的真实路径指向同一物理目录却未标注相同 `real_path`；全库扫描的文件计数与逐目录单独求和一致。

- **适用范围/来源**：本库初始化（2026-10-14）实际遇到的桌面 Junction 事实。**通用**：任何 Windows 上的目录盘点都要做这一步。



#### R-A-02 补充：不跟随子目录链接也可能漏掉录屏



- **症状**：用户确认刚用 Win+G 录制，但从 Videos 根目录搜索找不到近期 MP4。

- **原因**：本次 `C:/Users/UU189/Videos/Captures` 是 Junction，真实目标在 F 盘；默认不跟随链接的搜索没有进入该子目录。只检查 Videos 根目录是否为链接仍会漏掉。

- **修法**：先检查已知录制软件的预期保存子目录，用 `Get-Item -Force` 读取其 LinkType／Target，再直接检索真实目标一次。记录兼容路径和物理路径为同一实体，不对全盘盲目跟随所有链接。

- **验证**：解析 Captures 后找到 2026-10-18 21:30 的《云·异环》录像；源文件和项目副本 SHA-256 一致，原件保留。

- **适用范围／来源**：2026-10-18 乐谱自动演奏项目 v05 实际漏检与修复；适用于 Windows 已迁移的录制、下载等目录查找，不改变上文迁移盘点的去重要求。



### R-A-03 迁移计划里出现互相嵌套的条目



- **症状**：执行迁移时先移动了父目录，后面那条指向子目录的条目直接找不到源，或把刚移进去的东西又移一次。

- **原因**：盘点时对不同层级分别列了条目，计划本身没做包含关系检查。

- **修法**：`source` 只取**受支持的最小完整子树**，并且计划中任意两项不得互为祖先（互不包含）。同时禁止把源指向磁盘根（如 `C:\`、`F:\`）。

- **验证**：对计划做一次机器校验——两两比较规范化后的路径，若 `A == B` 或 `A` 是 `B` 的前缀目录，则报告冲突；目标路径必须落在库根之内。

- **适用范围/来源**：本库 `migration_plan.json` 的生成规则（2026-10-14）。已由 `99_迁移记录/tools/organize_ai_library.py` 的 `check_plan` 落实。

### R-A-04 EXE 归库后与便携数据分离，会读到另一份工作区



- **症状**：从归库后的新 EXE 位置启动，原设计不见或变成旧设计。

- **原因**：启动器优先 EXE 旁的数据文件夹，迁移只保留了旧桌面数据链接，没有在新 EXE 旁配套，回退到 AppData。

- **修法**：核对真实数据目录选择逻辑；交付 EXE 与经哈希核对的数据副本配套，保留原件，不通过文件迁移一致性推断启动一致性。

- **验证**：本轮清除 MANOSABA_DATA_DIR 后，独立 EXE 诊断的 data_dir 为相邻目录，当前三框模板预览通过。

- **适用范围/来源**：聊天框工作室 bugfix-20261015-v01 的 .NET 启动器和数据选择约定；不是所有 EXE 的统一存储规则。



## 类别 B：编码



### R-B-01 PowerShell 改文本文件会把中文搞成不可逆乱码



- **症状**：`.py` / `.md` 里的中文注释变成 `閿娇...`、`瑁呴厤鍖呭洿鐩?` 之类；脚本还能跑，但文档已坏。

- **原因**：`Get-Content`（旧版 PowerShell 默认按 ANSI/cp936 读）+ `Set-Content -Encoding UTF8` 写回，字节被错误解码，部分字符已丢成 `?`，**反向解码救不回来**。

- **修法**：改任何文本文件**只用编辑器/写入工具**，或走显式 UTF-8 的 Python 读写：

  ```python

  s = io.open(p, encoding='utf-8').read(); ...; io.open(p, 'w', encoding='utf-8', newline='').write(s)

  ```

  **文档不算「代码」，同样适用。**

- **验证**：不能只查 `U+FFFD` 替换符——乱码里根本没有这个字符，检查会「假通过」。必须**把改过的文件从头到尾读一遍**，肉眼确认是正常汉字。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-23 起，同一坑在 2026-09-28、2026-09-29 又踩两次（原文 6.1 / 6.2 / 12.6）。**通用**，但目前只在旧版 Windows PowerShell 5.1 上实测复现；本机现已是 pwsh 7.6.5，仍按最保守做法执行。



### R-B-02 输出重定向把中文报告写成 UTF-16



- **症状**：`python xxx.py > out\报告.txt` 生成的文件，用读取工具打开报「binary file」。

- **原因**：PowerShell 的 `>` 重定向按 UTF-16 带 BOM 落盘。

- **修法**：在 Python 内接管输出——把 `main()` 的 stdout 收进 `io.StringIO`，按 `utf-8 / newline='\n'` 写文件，同时转发到屏幕（原文的 `tools\run_report.py` 就是干这个的）。

- **验证**：用文本读取工具打开输出文件能正常显示中文，且首字节不是 `FF FE` / `FE FF`。

- **适用范围/来源**：`魔裁看守_建模` 项圈轮次，2026-09-28（原文 11.5）。



### R-B-03 文件名/命令行里的中文在外部服务上失败



- **症状**：带中文名的文件上传第三方服务时报 `'ascii' codec can't encode characters`；控制台输出中文乱码。

- **原因**：目标服务或控制台按 ASCII / GBK 处理。

- **修法**：对外传输前先复制一份改成 ASCII 名；命令行的中文改用「Python 写文件、再读文件」的方式传递，设 `$env:PYTHONIOENCODING='utf-8'`。

- **验证**：目标服务返回成功且能列回文件名；读回文件内容中文正常。

- **适用范围/来源**：原文《电脑发文件到手机》（2026-09-23）。**只对当时的这些服务实测过**；换服务需重测。



### R-B-04 `.ps1` 里的中文按 ANSI 解析



- **症状**：脚本内的中文字符串乱码。

- **原因**：旧版 Windows PowerShell 按 ANSI 读取无 BOM 的 `.ps1`。

- **修法**：给 `.ps1` 加 UTF-8 BOM（原文 `addbom.py`），或脚本内不写中文、中文从命令行传入。

- **验证**：`Format-Hex` 前 3 字节是 `EF BB BF`；脚本运行输出的中文正常。

- **适用范围/来源**：原文《电脑发文件到手机》第六节，绑定当时的 Windows PowerShell 5.1。**换到 pwsh 7 需重测，不要当成必然。**



### R-B-05 保留CRLF的字符串在Windows默认写入时产生重复空行



- **症状**：多次更新Markdown后空行增加，原始字节出现CRCRLF；中文和正文仍正常。

- **原因**：read_bytes().decode('utf-8')保留CRLF，默认文本写入又将其中LF转换为CRLF，形成重复CR。不能只检查编码和替换符。

- **修法**：先保存字节快照；本例把CR连续串加LF恢复成单个LF，用write_text(..., encoding='utf-8', newline='\n')显式写入，避免再次转换。不得对二进制文件或要求逐字节一致的原始素材做换行归一。

- **验证**：内存TextIOWrapper使用Windows换行规则复现CRCRLF；两份入口修订后均无CRCRLF。归一阶段去掉换行比较，正文字符保持一致；改动后全文回读、链接和哈希检查通过，旧版原字节保留。

- **适用范围／来源**：2026-10-21观众养成角色企划v09的Windows Python文本更新。证据见02_半成品/样片内容与数量_20261021_v09/换行验证_v09.json；不外推为所有文本都应统一换行。

## 类别 C：版本与验收



### R-C-01 只有「上次跑通留下的文件」不算交付



- **症状**：交付目录里有一份报告，但对应的脚本早就因为参数改名跑不通了——文件是上一次成功时的旧内容。

- **原因**：改了结构参数却没搜引用这些参数的脚本，交付脚本静默过期。

- **修法**：参数改名/改形时把引用这些参数的脚本全搜一遍（`grep` 一次就全露出来）；**交付前把所有交付脚本整体跑一遍**（build → 复查 → 受力 → 出图 → 打包），跑不通不算交付。

- **验证**：从干净副本完整跑一遍全链路，无 `KeyError`、无「跳过」；产物时间戳为本次运行时间。

- **适用范围/来源**：`魔裁看守_建模` 项圈轮次，2026-09-28（原文 11.6）。



### R-C-02 大改动前先做版本快照，失败版本也要留



- **症状**：一次编码事故把源文件写坏，没有可比对的旧版本，只能整篇重写。

- **原因**：没有在改动前留下可回滚的快照。

- **修法**：每次大改动前打快照（原文 `tools\snapshot.py` → `_versions\snap_*.zip`，改名成 `vNN_日期.zip`）；**失败的尝试同样保留**，它们是后续判断的依据。

- **验证**：列出快照目录，能查到「改坏之前」的那一版并成功解出原始文件。

- **适用范围/来源**：`魔裁看守_建模`（原文 6.5）；`电子幽灵` 工程同样保留 `motion_tests/r01`（风衣变形失败）与 `room_tests/r03`（早期建模）（见 `restart_state.json` 的 `retained_failed_motion_version`、`modeling_attempts_retained`）。**通用**：本库约定「保留所有版本、不删除、不覆盖同名文件、不按文件名自动去重」。

## 类别 D：图像与视频证据



### R-D-01 数值检查通过就交货，图上其实是坏的

- **原因**：数值判据只覆盖了它量的那一件事，没覆盖「形状是否可用」。

- **修法**：**出图 → 自己看图确认 → 有问题先改 → 再交付**。用户也明确要求过：不要看数据合适就直接交。

- **验证**：交付前必须有一次真实的看图记录（读图并描述看到了什么），不能只贴数值。

- **适用范围/来源**：`魔裁看守_建模` 弯钩爪，2026-09-27（原文 7.4）。**通用**。

### R-D-02 只看正视图，看不出贴合缝



- **症状**：正视图完全正常，用户斜着一看直接指出「圆锥和环的贴合有缝隙」。

- **原因**：平面锥底坐在弧面环带上，边缘必然翘起约 0.85mm，正视投影把它藏住了。

- **修法**：交付出图**必须带斜视角**，关键配合再补一张**剖切图**；数值 + 剖面图两条都过才算改好。

- **验证**：图集中存在斜视角与剖切图各至少一张，且能看到配合处。

- **适用范围/来源**：`魔裁看守_建模` 项圈，2026-09-28（原文 11.1）。



### R-D-03 相机方位角取 180° 会渲染出空白图



- **症状**：连续两次出的「正面图」都是全空白（3KB）。

- **原因**：相机朝向用 `to_track_quat('-Z','Y')`，方位角 180° 时视线与 up 提示向量平行，姿态退化。

- **修法**：正面视角不要取整 180°，用 200~210° 的近正视。

- **验证**：出图后**必须读图看一眼**（这次就是看图才发现的）；文件大小明显偏小也是信号。

- **适用范围/来源**：`魔裁看守_建模` 钥匙冠，2026-09-29（原文 12.9）。**只对这套渲染脚本实测**，换渲染管线需重测。



### R-D-04 视频「能播」不等于完整可解码



- **症状**：视频文件存在、能播前几秒，但整段解码时报错或帧数不足。

- **原因**：只做了抽查，没做完整解码。

- **修法**：验收视频必须**完整解码全片**（逐帧解到底），并记录时长、分辨率、帧率、帧数；无音轨的样片要显式标注「无音轨技术验证样片」。

- **验证**：全片解码无错误，帧数与「时长 × 帧率」一致。实例：`电子幽灵` 的 4 个既有 MP4（4/4/4/3 秒，1600×1024 / 24fps）在 `media_audit.json` 中全部通过完整解码；重启后 240 帧渲染完整保留并通过核验。

- **适用范围/来源**：`电子幽灵`，2026-10-13/14（`重启计划.md`、`restart_state.json` 的 `restart_recovery`）。



#### R-D-04 补充：变帧率录屏与 null 输出时间基



- **症状**：Win+G 录屏标称 60 fps，但 18.70 秒视频只有 534 个实际帧；默认全片解码到 null 出现一次 `non monotonically increasing dts` 提示，退出码却是 0。

- **原因**：标称帧率不能替代实际平均帧率和时间戳；本次保留输入时间基后提示消失，说明至少需要排查默认输出时间戳处理，不能仅凭这条 null mux 提示判定源片损坏。

- **修法**：记录 `r_frame_rate`、`avg_frame_rate`、实际读帧数和流记录帧数；VFR 不套“时长×标称帧率”判据。使用 `-fps_mode:v passthrough -enc_time_base:v demux -f null NUL`复检，保留初次提示、复检命令及 stderr，不改源片、不掩盖实际解码错误。

- **验证**：本项目两段完整读帧分别为 1050 和 534，与流记录一致；保留输入时间基的全音视频解码均退出 0，stderr 为空。

- **适用范围／来源**：2026-10-18 乐谱自动演奏 v09 的两段 Win+G 变帧率 MP4；不是对所有 DTS 错误的通用免检结论。



本规则在 2026-10-19 乐谱自动演奏 v15 的 RGB 提取中再次复现：



- **症状**：rawvideo 输出仅设 passthrough 仍产生重复 DTS 提示，弦色分析 v02 因 stderr 非空而停止。

- **原因**：本次 rawvideo 输出同样需要保留输入时间基，不能只给 null 完整解码设置该参数。

- **修法**：保留失败脚本，v03 对 RGB 输出增加 `-enc_time_base:v demux`，不改原视频。

- **验证**：输出无 stderr、退出 0，RGB 与 ffprobe 原 PTS 均为 2366 帧，弦色可按源 PTS 对齐。

- **适用范围／来源**：本次离线 rawvideo／RGB 分析调用，证据为 v15 的 `诊断与处理_v01.json`；其他源片和错误仍须独立核查。



### R-D-05 「没有干涉」是假证据——必须补正向证据



- **症状**：榫片槽「插得进去吗」的检查全部通过，实际**两件都没被切到**，榫片飘在离杆轴 165mm 的空中。

- **原因**：`A ∩ B = 0` 既可能是「刚好滑进去」，也可能是「**A 根本不在这儿**」。只查「没有干涉」会漏掉整类更离谱的错。

- **修法**：凡是「贴合 / 穿过」的判断，必须再补一条**正向证据**，例如「槽上方 1.4mm 的薄板 ∩ 杯壁 = 171 mm³ > 0」（证明槽周围确实有材料）、「两件的包围盒在轴向有交叠」。

- **验证**：检查脚本同时输出「干涉为 0」与「正向证据 > 0」两项，缺一不算通过。

- **适用范围/来源**：`魔裁看守_建模` 插座杯，2026-09-27（原文 9.5）。**通用**：任何「没报错」型的检查都要问一句「它是不是压根没检查到东西」。

## 类别 E：Blender 单位、几何与布尔



> ⚠ **范围警告**：本节规则来自 `魔裁看守_建模` 这一套参数化建模流水线（当时为 Blender 4.5 headless + `tools\py311\python.exe`）。

> 它们是**该流水线的约定与实测结论**，不是「所有 Blender/Python 环境都必须这样」。

> 换工程（例如 `电子幽灵` 用 Blender 4.2.23 LTS + `D:/AI/venv` 的 Python 3.12.0）必须重新确认单位与解释器。



### R-E-01 单位链：代码里是毫米、场景里是米、导出后是毫米



- **症状**：导出的 STL 只有几毫米，或大得离谱。

- **原因**：约定是 **1 Blender 单位 = 1 米**，几何用毫米建模，`make_object()` 用 `UNIT_SCALE=0.001` 转成米；导出时 `global_scale = 1000` 换回毫米。中间任何一步手改比例都会错。

- **修法**：记住这条链，别在中间改比例。手工在 Blender 里看尺寸要**乘 1000** 才是毫米；想改设计值请回脚本改参数重跑，**不要用缩放（S）改尺寸**（会破坏配合公差）。

- **验证**：导出后用切片软件（Cura / 拓竹 / PrusaSlicer）打开看尺寸；已知基准件应约为：长杆 ~1280mm / Ø25，刃根段 ~235×11×225mm。手工导出 STL 时「缩放」必须填 **1000.0**，否则差 1000 倍。

- **适用范围/来源**：`魔裁看守_建模`（原文《建模总结》1.2、`Blender改模指南.md` 第三、八节），2026-09-23。**仅对该流水线成立**。



### R-E-02 打印尺寸要按世界坐标量



- **症状**：报给用户的尺寸和 STL 文件量出来的差一个 90° 旋转。

- **原因**：脚本原来直接量 `v.co`（局部坐标）；而 STL 导出器会带上对象变换，导出的坐标 = 世界坐标。

- **修法**：一律用 `ob.matrix_world @ v.co` 再统计。

- **验证**：脚本量出的尺寸与解析 STL 文件量出的尺寸一致。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27（原文 8.2）。



### R-E-03 布尔会丢掉「贴着主体端面的独立小壳体」



- **症状**：尾销、刃根上延块、爪并进零件后，导出的 STL 里整块没了；或布尔一跑，原本正常的分件塌成几十个顶点。

- **原因**：Blender 的 EXACT 布尔在这种「贴着、独立成壳」的小块上会整块丢弃。多壳体切刀、自重叠壳体、共面切刀同样会算崩（实例：`Blade_6` 517 顶点 → 3 个顶点；`Fig8_Head` 1440 面 → 99 面）。

- **修法**：**顺序永远是「单实体 → 布尔 → 再 join/merge」**；所有布尔做完之后，再把这些小块 `join` 回去；多壳体切刀**分开做，一样一次布尔**；刻槽切刀两端各让开安全边距（默认 3mm）。

- **验证**：布尔后逐件比对顶点/面数没有异常塌陷；`bmesh` 数真开边（只被 1 个面用到的边）应为 0。

- **适用范围/来源**：`魔裁看守_建模`（原文 2.1、2.2、2.3、9.2、11.2）。**只在该流水线的 EXACT 求解器上实测。**



### R-E-04 布尔不能当测量工具——包围盒和求交都会给假证据



- **症状 A**：`Crow_Plug` 包围盒虚报 **341.8 × 82.0 × 324.3 mm**（真实 206.5 × 82.0 × 190.3）。

  **症状 B**：插座杯内孔照「柱体 Ø35.4」做成 Ø36.2，实测插入段最大半径只有 **10.0**，杯子里空着一大圈。

  **症状 C**：同一条 `销轴 ∩ 半圆` 的布尔求交，左右两边给出 0.49mm³ 与 272.83mm³，同一份几何**重跑还会变**。

- **原因**：

  - 包围盒 = 各轴极值的组合，**任何斜的/局部凸起都会把它撑大**（`柱体.stl` 的 35.4 是一圈珠子的外径撑出来的）。

  - 多壳体 + 共面对象上，EXACT 布尔会给出假体积（`Gothic_Handle ∩ 铝管` 报 14194mm³）。

  - 销轴整段埋在材料里时，EXACT 偶发把**整个销轴**当成交集，求交退化成原样返回。

- **修法**：

  - 尺寸按**截面**量：按轴分站，逐站打印 `hypot(y,z)` 的取值范围，一眼看出「这一段是 Ø20、那一段有个 Ø44 的珠子」。

  - **布尔只用来「挖」，不用来「量」**：判「能不能穿过去」改用采样 + 点在体内判定（三方向射线投票取多数），或改用**顶点判据**（有没有顶点落在配合面的半径带内）。

  - 用户手件是用户改过的，任何时候都不能拿旧测量值当准。

- **验证**：同一结论用两种独立方法各量一次并互相吻合；用「顶点判据 / 分站截面」这类不会假阳性的方法复核布尔结果。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27～29（原文 8.1、9.1、9.5、10.4、11.4、12.1、12.2）。**只在该流水线实测。**



### R-E-05 扫掠体的标架约定会随路径切线变化



- **症状**：整条刃长在刃缘另一侧、布尔等于没切；截面 12×6 变成 6×12 卡死在槽里；爪被扫成一排平行折痕。

- **原因**：`sweep()` 的默认 `ref=(0,0,1)` 在起点切线接近竖直时走回退分支，法向与约定**正好反向**；面索引按首站点数算，各站截面点数变化就全错；平行传输标架随路径切线转，相邻站转角过大时截面互相叠。

- **修法**：**永远显式给 `ref`**（用 `_blade_ref()` 返回与起点切线垂直的向量）；截面点数**恒定**；精确对位的小件**几何自己写死**（手写顶点），不依赖 sweep 的标架约定。判断阈值：**相邻站转角 > 25° 就要警惕**（实测 48° 起褶，参数化后降到 5.4°）。

- **验证**：打印每根扫掠体路径的相邻站最大转角与长度；渲染出图确认形状不是折痕。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-23～27（原文 3.1、3.2、7.2、7.3、9.6）。



### R-E-06 形变权重的边界只要位移不为 0 就会把网格抻开



- **症状**：小腿末端出现一圈多边形断口；趾根被抻成细长尖刺；或出现薄片。

- **原因**：按「沿趾方向的参数 t」加权时 `t=0` 是个**平面**，而腿是往上走的管子，该平面几乎与腿轴平行——同一横截面上半被卷走、半不动，腿被纵向劈开（实测脚踝截面 t 跨 −7…+16）。

- **修法**：让**权重边界落在位移本来就接近 0 的地方**（锥顶点、趾根），例如把权重改成以趾根为顶点的锥 `|s| < t·tanθ + c0`；实在不行就「重做几何」。

- **验证**：统计截面上参数的符号分布，确认没有「同一截面被切开」；出图确认没有尖刺/薄片。

- **适用范围/来源**：`魔裁看守_建模` 乌鸦，2026-09-27（原文 5.4、5.5）。



### R-E-07 `join` 之后再做整体旋转，并进来的零件会留在原地



- **症状**：把镰刀改成立姿后，弯钩爪从环体上掉下去；`join` 进来的零件包围盒虚报。

- **原因**：`bpy.ops.object.join()` 把源几何写进**目标对象的局部坐标系**（`v_local = M_target⁻¹ · v_world`）。目标已带 −90° 旋转时，并进来的几何被反向转回去，世界位置停在并之前。

- **修法**：**展示用的整体旋转只能放在最后一步**，所有 `join` / 布尔都做完之后再调用；`build_objects()` 之后新建的对象也要自己补一次。

- **验证**：给 `join` / 布尔打 monkeypatch，在每次前后打印目标的局部包围盒，看是否整块翻转。实例脚本：`tools\plug_trace2.py`。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27（原文 8.1）。



### R-E-08 界面操作的取舍：改 `.blend` 还是改脚本



- **症状**：手工改了 `.blend`，下次重跑重建脚本，改动全被覆盖。

- **原因**：工程是由脚本参数表生成的，`.blend` 只是产物。

- **修法**：想长期保留改动就改脚本参数（`P = dict(...)`）重跑；临时看效果才改 `.blend`，改完就别再跑重建脚本。**别用缩放（S）改尺寸**——会破坏配合公差。

- **验证**：重跑重建脚本后，改动仍在（说明改在脚本里）；或明确记录「这一版 `.blend` 不再重跑脚本」。

- **适用范围/来源**：`魔裁看守_建模`（`Blender改模指南.md`）。**只对参数化生成的工程成立**；手搭工程不适用。

## 类别 F：工具与协作



### R-F-01 诊断脚本复制了一份公式 → 改了实现它还报旧数据



- **症状**：把路径改成「转角集中在后段」，诊断仍报 73°，白折腾一轮。

- **原因**：诊断脚本里**又写了一遍**路径公式，改的是实现文件。

- **修法**：把被量的东西抽成一个函数，诊断脚本**直接调用**它。**凡是要「量」的东西，只能有一份实现。**

- **验证**：改实现后重跑诊断，输出数值随之变化。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27（原文 7.1）。**通用**。



### R-F-02 用数值检查代替「看图猜」（正确用法）



- **症状**：靠反复渲染试参数，一轮几分钟，试不动。

- **原因**：没有把「想要的性质」写成可计算的判据。

- **修法**：把性质写成一次扫描就能定参数的数值判据。实例：把每根爪的路径采样，算到环体表面的有符号距离，要求 ≥ 爪的局部半径；YIN 从 0.55→0.45→0.35→0.28 时穿模根数 6→5→2→0，一次扫描定参。

- **验证**：数值判据的结论与出图目视一致（**数值不能单独当验收**，见 R-D-01）。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27（原文 5.8）。



### R-F-03 `revolve()` 的 `closed=True`：首尾不在轴上的轮廓必须闭合



- **症状**：Collar 的 STL 有 96 条开边，手柄的两个箍环各有 64 条——都是开口壳。

- **原因**：`revolve(profile, segments)` 默认只连相邻两点；轮廓首尾都落在内孔半径上而不闭合，等于没建内孔那一圈面。

- **修法**：管/环内表面的轮廓一律 `closed=True`。

- **验证**：用 `bmesh` 数「只被 1 个面用到的边」，应为 0。**注意把「开边」和「多面边」分开看**：`link_faces == 1` 是真破洞要修；`link_faces > 2` 是壳体接触面贴合，几何闭合、切片没问题。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27（原文 10.2、10.3）。



### R-F-04 一维梁有限元的两个「鬼数」来源



- **症状**：30N 横向力算出自由端位移 1144mm、应力 3437MPa。

- **原因**：① 惩罚法边界元倍数取 `1e12 × max|K_ii|`，双精度有效位被吃掉（取 **1e6** 就够）；② 力的单位：位移用 mm、模量用 MPa 时力就是 **N**，不能再乘 1000。

- **修法**：出鬼数先查量纲；惩罚倍数用 1e6。复核办法是拿结果去对**手算的悬臂解** `δ=FL³/(3EI)`、`σ=M/W`。

- **验证**：数值解与手算解量级一致（本例 δ≈0.3~0.4mm、σ≈3.4MPa）。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27（原文 9.3）。**只对这套自写 FEA 脚本**。



### R-F-05 实心模型 ≠ 实心打印



- **症状**：按实心网格算质量，荷载算大 3 倍。

- **原因**：4 层壁 + 15% 填充的厚实体只用到约 30% 材料。

- **修法**：质量特性从**真实网格**积分（`tools\joint_fea.py`：`V=Σ a·(b×c)/6`），算荷载时再乘填充系数。

- **适用范围/来源**：`魔裁看守_建模`，2026-09-27（原文 9.4）。**只适用于 FDM 打印件估算。**

## R-G-59：公开下载与日志先保留原始字节，再按实际格式解释
