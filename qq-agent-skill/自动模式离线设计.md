# 自动转图：离线设计，尚未接入宿主

目标：管理者打开开关后，机器人本轮原本要发的文字，优先制作为聊天框图片；关掉后沿用原本发送流程。现有按需调用工具不满足此目标，只作为历史原型保留。

## 已核实的范围

社区 fork 的 `orchestrator.js` 在收到模型响应后调用 `after-response`，之后才读取 `response.message.tool_calls`。对包含原生 `send_message` 的调用，可以在这一点改名，但插件 hook 不能自己发送消息；发送工作必须由工具完成。普通工具有本次会话的 `ctx.chatKey` 和 `ctx.sender`。

关键障碍：宿主每次会话的 `toolDefs` 快照是局部变量，`after-response` 的上下文没有该快照；`session.excludedTools` 不能证明某个工具存在。工具热加载、分类关闭或工具被禁用时，盲目改名可能导致“未知工具”和回复丢失。因此不能直接在现有 hook 内启用该改写。宿主需要明确向该 hook 提供 **本轮实际可执行工具名称的快照**，并保证执行时使用同一快照；否则绝不改写。

本文件同目录 `automatic-prototype.mjs` 只演示以宿主可信快照为前提的改名判断，不是可安装插件、不调用 QQ、不发送消息。需在真实目标版本确认该协议并提供宿主支持后才能进一步实现。

## 建议处理顺序

1. 开关关闭，或快照未提供、格式不对、原工具和目标工具任何一个缺失：原调用保持不变。
2. 只改原生 `send_message` 的工具名，保留调用 ID、原始参数（包含 `messages`、`replyToMessageId`、`atUserId`），不从用户消息猜测要发送的文字或目标会话。
3. 目标工具接收宿主同一套消息归一化结果，按顺序逐条用于排版；保留引用和 @ 参数。每条最多 240 字且能排版时先渲染。图片必须在受控临时目录内验证后，调用 `ctx.sender.sendImage` 发送到 `ctx.chatKey`；仅用受控随机文件路径作去重键。宿主发送完成后才清理临时文件。仅使用文件路径要求协议端能访问同一文件系统，但避免此 fork 对超时文件自动回退 base64 的潜在重复。
4. 长度超过限制、字体/模板缺失或其他在发送前就明确发生的渲染故障：调用原宿主文本工具一次，原样传参数，避免丢字。发送图片后若返回超时等不确定结果，不自动回退文本或重试，以免重复发送；提示结果不确定，待检查。
5. 保留宿主队列、限频与记录；只有实际发送成功才登记相应 `session.sent` 并通知 UI。发图的留档文字需与模型上下文的连续对话一致，这一点需在真实宿主中验证。

## 限制

此路径只覆盖原生模型工具调用。宿主事后解析正文中的 inline 调用、回复抢救生成的调用、提醒和其他插件直接发送，不经过此位置，不能说已全覆盖。并发、工具调用多条、工具开关中途变化和图片网络结果不明确均需要针对实际版本联调。应由目标宿主增加可靠的出站转换能力，才能追求完整覆盖。
